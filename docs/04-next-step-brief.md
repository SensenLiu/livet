## 你需要交付的两份方案

### 方案 1：产品设计方案（Product Design Spec）

**目标读者**：未来的产品/设计/工程师团队（哪怕暂时只有创始人自己）

**必须覆盖**：

#### 1.1 用户体验设计
- 三种交互模式（🟢主动询问 / 🟡被动提示 / 🔴守护监听）的具体 UX
- 首次启动引导流程（如何让用户在 60 秒内理解"重要时刻一键启动"+ 选 2-3 个场景）
- 各场景包的具体使用流程（每个场景从启动到结束的完整 user journey）
- 被动提示的具体形态设计（耳机声音设计、字幕样式、震动模式）
- 长期记忆的用户可见呈现（一日复盘报告长什么样、成长档案怎么访问）

#### 1.2 关键页面与组件
- 首页（已选场景包入口、近期记忆、复盘）
- 场景启动页（一键启动、模式选择、提示方式选择）
- 场景进行中页（被动提示流、当前转写实时显示）
- 复盘页（一日总结、跨场景检索、成长档案）
- 设置页（隐私控制、模式切换、数据导出/删除）

#### 1.3 4 个 MVP 场景包的详细设计（首批 S1/S2/S5/S8）
- 每个场景的：启动条件、监听内容、提示规则、记忆提取、复盘模板
- prompt 工程：每个场景的系统 prompt 草稿
- 评估集设计：怎么量化"提示准不准""记忆抽取对不对"

#### 1.4 长期记忆引擎设计
- 数据模型（事件、人物、情绪、未决事项的 schema）
- 写入流程（场景结束 → 提取结构化记忆 → 入库）
- 检索流程（场景启动/决策时 → 跨场景 RAG → 注入上下文）
- 数据增长管理（如何避免老用户数据库膨胀、如何清理低价值记忆）

#### 1.5 隐私引擎设计
- "永不保留原声"的具体实现（流式处理、内存缓冲、定时销毁）
- 用户数据控制面板（查看/导出/删除/选择性遗忘）
- 端到端加密的多端同步（如果做）

**交付形式**：建议写到 `/home/lss/life_crutch/docs/10-product-design.md`，分章节，附必要的 mermaid/ASCII 流程图，关键页面用 ASCII 布局或文字描述。

### 方案 2：开发方案（Engineering Plan）

**目标读者**：开始动手写代码的人（独立全栈工程师 + AI 编程工具）

**必须覆盖**：

#### 2.1 技术栈最终决策
- 前端：React Native? Flutter? 哪个？（plan v3 暂定 RN，请确认或推翻）
- 端侧 VAD 选型：Silero VAD vs WebRTC VAD vs 自训
- ASR 选型：讯飞 vs 阿里 vs 火山 vs 多供应商路由
- TTS 选型：CosyVoice vs ElevenLabs 国内 vs 自训
- 大模型选型：DeepSeek + 豆包双供应商的实际路由策略
- 本地数据库：SQLite + sqlite-vec（RAG 用）的具体方案
- 音频流处理：WebSocket vs LiveKit vs 自建

#### 2.2 模块划分与目录结构
- 把 plan 里的目录结构（`app/src/modes/`, `app/src/scenarios/`, `app/src/core/`, `gateway/`, `prompts/`）落实成可执行的代码骨架
- 各模块的接口定义（TypeScript 类型/接口）
- 模块间依赖关系图

#### 2.3 关键技术点的 PoC 路径

每个关键技术点写出"如何在最短时间内做出能运行的 demo"：

- **PoC-1**：流式音频接入 + ASR 转文字（不接大模型）
- **PoC-2**：端侧 VAD + 智能唤醒
- **PoC-3**：被动提示形态测试（耳机声音 + 字幕同步）
- **PoC-4**：长期记忆引擎最小版（一个场景的写入+检索）
- **PoC-5**：iOS 后台持续录音的合规实现
- **PoC-6**：Android 前台服务的合规实现

每个 PoC 给出：技术方案、依赖库、关键代码片段、验证标准、预估耗时（人日）。

#### 2.4 阶段 0（0-3 个月）开发计划
按周分解 12 周开发任务，每周给出：目标、交付物、风险、降级方案。

#### 2.5 关键风险与降级方案
- 如果端侧 VAD 误激活率太高怎么办？
- 如果 iOS 审核拒了"持续录音"怎么办？
- 如果大模型 API 成本超预期怎么办？
- 如果"何时被动提示"算法做不出可用版本怎么办？

#### 2.6 测试策略
- 评估集（每个场景的输入/期望输出对）
- 内部 dogfooding（创始人和共创群 8 人先用 4 周）
- Alpha 测试（30 个亲友 2 周）
- Beta 测试（小红书招募 100 人 2 周）

**交付形式**：建议写到 `/home/lss/life_crutch/docs/11-engineering-plan.md`。

## 工作原则（必须遵守）

1. **遵守 4 条产品哲学铁律**（见 `01-philosophy.md`）。任何违反铁律的设计都该重新做。
2. **基于已决战略不翻案**（见 `02-decisions-log.md` 的 11 条决策）。除非用户主动要求重审。
3. **务实**：用户是个人探索阶段，方案要"今天就能开始做"。不要写需要 30 人团队才能落地的方案。
4. **遇到 9 个开放问题**（见 `03-open-questions.md`）：可以提出建议、列利弊，但**最终决定权交给用户**，不要替他拍板。
5. **数据来源诚实**：如果某个技术点你不确定（如某个 SDK 是否真支持某个特性），明确标注 `〔需验证〕`，不要瞎写。
6. **写完后让用户 review**：每写完一份方案，主动告诉用户哪些点你最不确定、哪些点最希望他先看。
